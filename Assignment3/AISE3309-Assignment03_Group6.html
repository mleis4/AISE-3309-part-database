0.1  Implementation decision: no triggers

Section 2.4 of the A2 report says triggers will maintain C3, C5 and C7. In A3 the group uses no triggers, because the handout only asks us to "consider" them. The A3 report should say so and explain how each constraint is handled instead:

ConstraintWhy the DBMS cannot enforce itHow it is upheld
C3 (a selection must be for a part the BOM contains, at most one per part)It spans BOMSelection, Listing and BOMLine, so the ISO form is CREATE ASSERTION, which MySQL does not supportData generator and A4 application; check_data.sql query
C4 (Part1 < Part2, no self-pair)The ISO CHECK is rejected by MySQL error 3823 because the columns have FK referential actionsData generator and application; check_data.sql query
C5 (a shared BOM has at least one line)Needs CREATE ASSERTIONData generator and application; check_data.sql query
C7 (a listing's part never changes)A rule about updates, which no assertion can expressThe application never updates those columns

1.1  Design decisions

DecisionChoice and reason
Data typesVARCHAR for names, emails and part numbers (Email VARCHAR(254), the longest legal address); DECIMAL(10,2) for money; INTEGER for quantities, stock and ratings; DATE for creation dates; TIMESTAMP for Listing.LastUpdated. ISO CREATE DOMAIN would define each shared domain once; MySQL lacks it, so the type is repeated.
KeysNamed constraints: pk_, ak_ (UNIQUE), fk_, ck_. Every FK column is NOT NULL with ON UPDATE CASCADE; ON DELETE (CASCADE or RESTRICT) is taken from the A2 referential integrity table.
CHECK (C1 and domains)StarRating BETWEEN 1 AND 5; Quantity > 0; UnitPrice, StockQuantity, EstShipTime and ShippingFee >= 0; positive dimensions; Packaging IN a fixed list (instead of MySQL's ENUM). Enforced by MySQL 8.0.16 and later.
C2 and C6C2 is the alternate key ak_Listing_1 (DistributorName, ManufacturerName, Manufacturer_PartNum, Packaging). C6 is the primary key of Review.
Optional attributesLeft nullable: Customer.UnitNum, Part.Description, the three dimensions, Part.Datasheet_link, SharedProject.Description, Review.ReviewText.
IndexesInnoDB already indexes every PK, UNIQUE and FK. Two are added: Part(Category) for the category filter, and Listing(ManufacturerName, Manufacturer_PartNum, UnitPrice) for Price Match.
Derived attributesNot stored (A2 decision). They are computed in queries and the BOMTotals view.
TriggersNone (group decision). C3, C4, C5 and C7 are documented at the end of task3.sql in their ISO form (CREATE ASSERTION or CHECK) and verified by SRC/check_data.sql (section 3.3).

1.4  Constraints not enforced by the DBMS

-- Constraints not enforced by the DBMS
-- ----------------------------------------------------------------------------
-- C1 (ranges), C2 (Listing AK), C6 (Review PK) and every FK are enforced above.
-- The four rules below cannot be written as a key or a CHECK that MySQL
-- accepts. The group decided not to use triggers, so each rule is written in
-- its ISO form for the record and upheld outside the DBMS:
--   * SRC/generate_data.py asserts it before writing load_data.sql,
--   * the Assignment 4 application checks it on every change, and
--   * SRC/check_data.sql has a query that returns 0 rows when it holds.
--
-- C3: a BOM selects only listings of parts it contains, at most one per part.
--   It spans BOMSelection, Listing and BOMLine, so the ISO form is an
--   assertion (C&B ch. 7). MySQL does not support CREATE ASSERTION.
--
--   CREATE ASSERTION SelectionMatchesLine CHECK (NOT EXISTS (
--       SELECT * FROM BOMSelection s JOIN Listing l
--              ON l.DistributorName = s.DistributorName
--             AND l.Distributor_PartNum = s.Distributor_PartNum
--       WHERE NOT EXISTS (
--           SELECT * FROM BOMLine b
--           WHERE b.CustomerEmail = s.CustomerEmail
--             AND b.BOM_name = s.BOM_name
--             AND b.ManufacturerName = l.ManufacturerName
--             AND b.Manufacturer_PartNum = l.Manufacturer_PartNum)));
--
--   CREATE ASSERTION OneSelectionPerPart CHECK (NOT EXISTS (
--       SELECT s.CustomerEmail, s.BOM_name, l.ManufacturerName, l.Manufacturer_PartNum
--       FROM BOMSelection s JOIN Listing l
--              ON l.DistributorName = s.DistributorName
--             AND l.Distributor_PartNum = s.Distributor_PartNum
--       GROUP BY s.CustomerEmail, s.BOM_name, l.ManufacturerName, l.Manufacturer_PartNum
--       HAVING COUNT(*) > 1));
--
-- C4: AlternativeTo is symmetric and irreflexive. Each pair is stored once,
--   with the smaller part key first. The ISO form is a table CHECK:
--
--   CONSTRAINT ck_PartAlternative_order CHECK (
--       (Part1_ManufacturerName, Part1_PartNum) < (Part2_ManufacturerName, Part2_PartNum))
--
--   MySQL rejects it with error 3823 ("Column cannot be used in a check
--   constraint: needed in a foreign key constraint referential action"),
--   because all four columns have ON UPDATE CASCADE / ON DELETE CASCADE.
--   The Assignment 2 referential actions are kept rather than weakened to make
--   the CHECK fit. Queries read each pair in both directions (Task 4).
--
-- C5: a SharedProject's BOM always has at least one BOMLine.
--
--   CREATE ASSERTION SharedBOMNotEmpty CHECK (NOT EXISTS (
--       SELECT * FROM SharedProject p
--       WHERE NOT EXISTS (
--           SELECT * FROM BOMLine b
--           WHERE b.CustomerEmail = p.CustomerEmail
--             AND b.BOM_name = p.BOM_name)));
--
-- C7: the part offered by a listing never changes.
--   This is a rule about UPDATE (old value vs. new value), which no CHECK or
--   assertion can express: both only see the current state. The application
--   never updates Listing.ManufacturerName or Listing.Manufacturer_PartNum; an
--   offer for a different part is inserted as a new listing. The only change
--   to those columns is the ON UPDATE CASCADE from Part when a part's own key
--   is corrected, and then the listing still refers to the same part.
-- ============================================================================

3.  Task 3: Substantial Data Loading

SRC/generate_data.py (Python 3, standard library only, fixed seed 3309) fabricates the data and writes SRC/load_data.sql: multi-row INSERT INTO ... 3.2  Coverage of edge cases

  • 12% of parts have no listing; 12% of listings have stock 0, so stock filters change results.
  • 20% of (distributor, part) pairs come in 2 or 3 packagings, so C2 and the price comparison have real choices.
  • Generic parts (1N4148, 2N3904, LM358, NE555, L7805) are made by several manufacturers: the reason for the composite part key.
  • About 29% of BOM lines have no selected listing (non-zero /UnpricedParts); 41 BOMs have no lines at all; 69 customers have no BOM; 17 carts are empty.
  • Shared-project titles repeat across customers (the AK is per customer).

6.1  Are the views updatable?

The ISO rules (Connolly & Begg, ch. 7) used below

A view is updatable only if: 1. DISTINCT is not specified; 2. every element in the SELECT list is a column name (no expressions, constants or aggregates), and no column appears more than once; 3. the FROM clause names exactly one table (no joins, UNION, INTERSECT or EXCEPT); if that table is a view, it must be updatable too; 4. the WHERE clause has no nested SELECT that refers to the table in FROM; 5. there is no GROUP BY or HAVING.

In addition, an INSERT through a view fails if the view leaves out a NOT NULL column with no default, and WITH CHECK OPTION rejects an INSERT or UPDATE through the view that would produce a row the view's WHERE clause does not select.

V1: BOMTotals (not updatable)

CREATE VIEW BOMTotals (CustomerEmail, BOM_name, NumberOfParts, UnpricedParts, TotalCost) AS
SELECT b.CustomerEmail, b.BOM_name,
       COUNT(bl.Manufacturer_PartNum),
       COUNT(bl.Manufacturer_PartNum) - COUNT(l.UnitPrice),
       COALESCE(SUM(bl.Quantity * l.UnitPrice), 0)
FROM BOM b LEFT JOIN BOMLine bl ON ... LEFT JOIN (BOMSelection s JOIN Listing l ON ...) ON ...
GROUP BY b.CustomerEmail, b.BOM_name;
  • Purpose: the derived attributes of BOM from Assignment 2, computed once for all 802 BOMs, so the app's BOM page does not repeat the Q3 join. The derived values are never stored (A2 decision), so the view stays correct after any change to lines, selections or prices. The column list after the view name names the computed columns.
  • Logic: the same as Q3 without the customer filter (see Q3 for the outer-join and COUNT reasoning).
  • Relational algebra: BOMTotals = πCustomerEmail, BOM_name, NumberOfParts, NumberOfParts−Priced, TotalCost(γCustomerEmail, BOM_name; COUNT(Manufacturer_PartNum)→NumberOfParts, COUNT(UnitPrice)→Priced, SUM(Quantity·UnitPrice)→TotalCost(BOM ⟕ BOMLine ⟕ (BOMSelection ⋈ Listing)))
  • Query on the view: shared projects whose BOM is fully priced (UnpricedParts = 0) and has at least 7 parts, joined with SharedProject for the title. Result: 4 projects, from $420.36 down to $15.42. A view is used in FROM like a base relation; the DBMS merges or materialises the view definition when the query runs.
  • Modification attempts and responses:
  • INSERT INTO BOMTotals ... VALUES ('alex.chen0@example.com', 'New BOM', 0, 0, 0.00) → ERROR 1471: The target table BOMTotals of the INSERT is not insertable-into
  • UPDATE BOMTotals SET TotalCost = 0 WHERE ... → ERROR 1288: The target table BOMTotals of the UPDATE is not updatable
  • Why it is not updatable (ISO rules):
  • Rule 2 is broken: NumberOfParts, UnpricedParts and TotalCost are aggregates and expressions, not column names. Setting TotalCost = 0 would mean changing an unknown mix of quantities and prices in two other relations.
  • Rule 3 is broken: FROM joins four relations (BOM, BOMLine, BOMSelection, Listing), two of them through outer joins.
  • Rule 5 is broken: it has GROUP BY. Each view row stands for a whole group of base tuples, so there is no single base tuple an inserted row could become.
  • Rules 1 and 4 hold (no DISTINCT, no subquery in WHERE), but one broken rule is enough.
  • MySQL agrees: MySQL can update some join views (when one base table is changed and the view has no aggregates), but any view with GROUP BY or aggregate functions is neither updatable nor insertable, which is what errors 1288 and 1471 say.

V2: InStockListing (updatable, WITH CHECK OPTION)

CREATE VIEW InStockListing AS
SELECT DistributorName, Distributor_PartNum, ManufacturerName, Manufacturer_PartNum,
       Packaging, UnitPrice, StockQuantity, EstShipTime, LastUpdated
FROM Listing
WHERE StockQuantity > 0
WITH CHECK OPTION;
  • Purpose: the listings that can be bought now; the default data source for Price Match and the "in stock only" filter. It also lets an "add an in-stock offer" screen insert through the view while being unable to create out-of-stock rows.
  • Relational algebra: InStockListing = σStockQuantity>0(Listing) (all attributes kept, so the projection is the identity).
  • Query on the view: every in-stock offer for 1N4148, joined with Distributor for the shipping fee. Result: 6 offers, from $0.09 to $0.25.
  • Modification attempts and responses:
  • INSERT of a DigiKey listing for onsemi 1N4148 with StockQuantity 500 → Query OK, 1 row affected. The follow-up SELECTs show the tuple both in the view and in the base relation Listing: an insert through a view is an insert into its base table.
  • INSERT of a listing with StockQuantity 0 → ERROR 1369: CHECK OPTION failed 'ep_sourcer_test.instocklisting'.
  • UPDATE setting that listing's StockQuantity to 0 → ERROR 1369 again.
  • UPDATE setting its price to 0.08 and stock to 450 → Rows matched: 1 Changed: 1 (the row stays inside the view).
  • Why it is updatable (ISO rules):
  • Rule 1: no DISTINCT. Rule 2: every SELECT element is a plain column of Listing, each once. Rule 3: FROM names one base table. Rule 4: the WHERE clause (StockQuantity > 0) has no subquery. Rule 5: no GROUP BY or HAVING. All five hold.
  • Every view row therefore corresponds to exactly one Listing tuple, so the DBMS knows which base tuple to update, delete or insert.
  • INSERT works because the view keeps every NOT NULL column of Listing; if it left out, say, EstShipTime, an INSERT through it would fail because that column has no default.
  • WITH CHECK OPTION is why attempts 2 and 3 fail: the resulting rows would have StockQuantity = 0, which the view's WHERE clause does not select. Without it, attempt 2 would succeed and the new row would immediately "disappear" from the view (a migrating row), and attempt 3 would move an existing row out of the view.
  • The base-table constraints still apply through the view: the INSERT is checked against pk_Listing, ak_Listing_1 (C2), both FKs and the CHECKs, exactly as a direct INSERT into Listing would be.
